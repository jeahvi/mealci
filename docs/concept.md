# MealCI —— 给每一单麦当劳跑一次「提交前流水线」

> WorkBuddy × 麦当劳 1024 程序员节创意开发大赛 · 参赛 Skill 构思案
> 定位：不是热量计算器，不是省钱计算器，是**把下单变成一次代码合入**。

---

## 一句话

你说"想吃点啥"或者甩过来一个购物车，MealCI 把这一单当成一次 `git push`，先跑完 lint → test → build → review 四道流水线，最后给你一张 PR 卡：**✅ Ready to merge** 或 **⚠️ Changes requested**。确认后代你下单（支付你自己来）。

## 为什么这个不大众化

大赛里大概率会扎堆出现：热量估算、优惠凑单、随机点餐轮盘、减脂配餐——这些都是把 MCP 当**查询接口**用，一个函数调完就结束。

MealCI 的差异点在于**流程隐喻**：

1. 别人输出"答案"，MealCI 输出"评审意见"——产品叙事本身就是程序员节的主题；
2. 它不是调一个接口，而是把麦当劳 MCP 的**全部原子能力编排成一条链**：菜单、营养表、优惠券、报价下单、订单查询（历史）、门店（取餐预估），一个不落；
3. 交互语言全程 CI/CD 黑话，评委看到的第一眼就知道这是为 1024 定制的，不是平时也能用的通用工具。

## 四道流水线

### Stage 1 — lint（营养检查）
- 调营养表 MCP，给购物车每一项打标：🔴 钠超红线 / 🟡 热量档位偏高 / 🟢 通过
- **超线不拦截，给 diff**："把可乐换成零度，-190 kcal——像删掉一行冗余代码。"
- 一键 apply 修改，购物车原地更新

### Stage 2 — test（钱包测试）
- 拉优惠券 MCP，穷举当前订单的优惠组合
- 输出测试报告："✅ 2 tests passed：可比裸点省 ¥7.5（券组合 A）"
- 省钱是跑出来的，不是算出来的

### Stage 3 — build（取餐构建）
- 调门店接口估取餐时长，对齐你的工作节奏
- "预计 12 分钟取餐——够你 review 完手头这个 PR 再走。"

### Stage 4 — review（习惯评审）
- 调订单查询 MCP 拉近期历史，产出一句 standup 风格评语
- "本周第 4 次麦辣鸡腿堡。这属于技术债，建议本单 refactor 成板烧。"
- 连续多单无蔬菜 → "检测到循环依赖，要不要注入一份蔬菜沙拉？"

### 合入
- PR 卡展示最终价格 + 全部检查结果，点确认 → 报价下单 MCP 代下单
- 支付环节始终由用户自己完成（合规红线）

## 彩蛋（做 2-3 个就够）

| 触发条件 | 彩蛋输出 |
|---|---|
| 23:00 后下单 | lint 切入 strict 模式："警告：此单属于 hotfix，建议回滚（睡吧）" |
| 连续 5 单同款 | "检测到循环依赖，已尝试注入 break 语句（推荐一款没吃过的）" |
| 合入成功 | 输出 mock commit："feat(order): 双层堡×2 + 零度可乐, all checks passed 🍔" |
| 优惠券清零 | "CI 环境变量缺失：$COUPON 为空，本单按原价构建" |

## 技术落点（WorkBuddy Skill 形态）

- **形态**：Agent Skill（SKILL.md + 提示词编排），自然语言触发，无需 UI
- **MCP 依赖**：麦当劳官方 MCP（menu / nutrition / coupon / order / store）
- **输出物**：对话内渲染 PR 卡（文本表格即可，无需前端）
- **最小可行路径（MVP）**：lint + test 两道 + PR 卡 + 代下单确认；review 和彩蛋作为加分迭代

## 备选方案（已否决，留档）

| 方案 | 否决原因 |
|---|---|
| 团队拼单满减优化器 | 太工具化，任何电商平台都能做，跟"程序员节"无关 |
| 麦门塔罗 / 随机餐轮盘 | 官方 JD 里"按心情生成麦旋风"已经是示例脑洞，撞车 |
| 加班 crontab 夜宵助手 | 依赖对用户作息的判断，对话里拿不到稳定输入，容易翻车 |
| 热量估算 + 档位配餐 | V2EX 已有参赛作品「热麦卡路里」，正面撞车 |
